# Contributing to agda-lattices

Thank you for your interest in agda-lattices.  This guide says how a
contribution is checked, how a module joins the library, and what happens to
a pull request once it is opened.  The [README](README.md) says what the
library holds and how it is released; read it first.

## Before you start

+  **Open an issue first** for anything larger than a small correction: a new
   module, a new statement, a change to the type of a statement, or a change
   to the checks.  The issue lets the maintainer say where the work fits, or
   whether it is already under way, before you invest in it.
+  **A correction to a module** (a wrong citation, a misleading sentence, a
   proof that could be shorter) is welcome as an issue alone; a pull request
   is welcome too.
+  **The modules are published by release**.  The modules under `src/` are
   exported to this repository from the library's source repository, byte for
   byte, and `src/` changes only by such an export (the README's section on
   releases says how).  A pull request that adds or changes a module is still
   the way to contribute one; [What happens to a pull
   request](#what-happens-to-a-pull-request) says how it reaches a release.
+  **Licensing**.  The library is licensed under the Apache License 2.0
   (`LICENSE`).  By its section 5, a contribution you submit is licensed under
   the same terms, unless you say otherwise in the pull request.

## The environment

The toolchain is the repository's [Nix][] flake, and nothing else is needed:
Nix 2.28 or later, with flakes enabled.  The README's section "Checking it"
says how to fetch the pre-release Agda from the public binary cache instead
of building it.

    git clone https://github.com/ualib/agda-lattices.git
    cd agda-lattices
    nix develop

`nix develop` pins Agda 2.9.0 (a pre-release), the standard library 2.3
patched for it, and the Agda Universal Algebra Library at the commit
`flake.lock` names.  It writes a project-local Agda configuration under
`.agda/` and a wrapper, `.agda/bin/agda`, that runs the pinned Agda with that
configuration, so nothing in your own Agda configuration takes part.  To
check files from an editor, launch the editor from inside `nix develop`, or
point it at that wrapper.

## Checking a contribution

Run these from the repository's root, inside `nix develop` (or prefix each
with `nix develop --command`).  CI runs `make check`, the safety check's cases
and `make check-links` on every pull request (see [The
review](#what-happens-to-a-pull-request)).

### `make check`

`make check` runs the safety check (`make safety`, `scripts/check-safety.sh`),
generates the aggregator `src/EverythingLattices.agda`, which imports every
module under `src/`, and type-checks it.  It exits 0 when every module
checks.  On the library as it stands it prints, apart from Agda's own
progress lines, the following:

    target: safety
    bash scripts/check-safety.sh src
    safety: 81 modules, each with the pragma and no postulate or unsafe pragma
    target: EverythingLattices.agda
      wrote src/EverythingLattices.agda (81 modules)
    target: check
    agda +RTS -M6G -A128M -RTS  src/EverythingLattices.agda

The aggregator is generated by `find`, so a new module is checked as soon as
its file is in the tree; there is no list to edit.  The first run also checks
the modules of the Agda Universal Algebra Library that this library imports
and keeps their interfaces under `.deps/`; after that, a check of the whole
library from clean took about 100 seconds on the maintainer's machine.

### `make safety-test`

`make safety-test` runs the cases of the safety check
(`scripts/test-check-safety.sh`), the last of which runs the check on `src/`.
Run it whenever you change `scripts/check-safety.sh`.  It prints one line per
case and ends with the following:

    ok    src
    test-check-safety: all cases pass

### A new module's links

The documentation site resolves a module's name in prose, such as
`[Lattices.Dual][]`, through the generated `docs/_links.md`.  A pull request
that adds a module regenerates that file and checks every reference the
prose makes, as follows:

    make gen-links
    make check-links

`make check-links` fails if `docs/_links.md` is out of date or if any
reference has no definition.  On the library as it stands it ends with the
following:

    docs/_links.md is up to date.
    python3 scripts/python/check_links.py
    ✓ all reference-style links resolve (82 pages checked).

### The cost of a module

A module that takes three seconds or more to check on its own is **heavy**
(see [Cost and barrels](#cost-and-barrels)).  To measure, profile a check of
the whole library from clean and read the module's line, as follows:

    make clean
    make PROFILE=modules profile

The output ranks every module the run checked by the time it took (the
modules of the Agda Universal Algebra Library among them, on a run that
builds their interfaces).  On 2026-10-30 the head of that ranking was the
following, the five heavy modules above three seconds and every other module
below it:

    Total                                      106,903ms
    Miscellaneous                                2,570ms
    Lattices.Nation.NoCycle                     31,381ms
    Lattices.Nation.Lemma554                    20,211ms
    Lattices.Nation.Lemma551                     4,478ms
    Lattices.Examples.CountableFree              3,050ms
    Lattices.Nation.Lemma547                     3,029ms
    Lattices.Nation.Bounded                      2,794ms

A module near the threshold can fall on either side of it from one run to
the next; measure it more than once.

## How a module joins the library

The rules below describe the modules as they stand, and say so where a
module does not yet follow one; when in doubt, follow the modules beside
yours.

### Name and place

+  A module's name is `Lattices.` followed by its path under `src/Lattices/`:
   `Lattices.Nation.Lemma554` is `src/Lattices/Nation/Lemma554.lagda.md`.
   Worked examples go under `Lattices.Examples`.
+  **A published name is kept**.  Once a module or a definition is in a
   release, its name does not change silently.  To rename one, keep the old
   name beside the new for at least one release, with a warning:
   `{-# WARNING_ON_USAGE old-name "..." #-}` after the old definition, or, for
   a module, the old module re-exporting the new with
   `{-# WARNING_ON_IMPORT "..." #-}`.  Both pass `--safe` and the safety
   check.  The same holds for a change to a published definition's type: add
   the new definition beside the old, and deprecate the old.

### The file

+  **Literate Markdown**.  Every module is a `.lagda.md` file: prose, with the
   code in fenced `agda` blocks between the paragraphs, and the prose says
   what the code defines and proves.
+  **Front matter**.  Every module opens with front matter of the following
   form (this is `Lattices.Bounded.Covers`'s), and its first heading after it
   is a `###` heading naming the module's subject:

       ---
       layout: default
       file: "src/Lattices/Bounded/Covers.lagda.md"
       title: "Lattices.Bounded.Covers module"
       date: "2026-10-22"
       author: "the agda-lattices development team"
       ---

   A heavy module adds the line `check-cost: heavy` before the closing `---`.
   Most modules say next which module they are, as
   `This is the [Lattices.Bounded.Covers][] module of the [agda-lattices][]
   library.`
+  **The pragma**.  Every module's code begins with
   `{-# OPTIONS --without-K --exact-split --safe #-}`, its one `OPTIONS`
   pragma, ahead of its first declaration, and holds no `postulate` and no
   pragma that switches a check off (`TERMINATING`, `NO_POSITIVITY_CHECK` and
   the like).  A worked example, under `Examples/`, may add
   `--lossy-unification` to that pragma, and should say why
   (`Lattices.Examples.Central` does); no other module may.
   `scripts/check-safety.sh` enforces all of this.
+  **The header block**.  Most modules put the pragma, the `module` line and
   the imports in one block of code inside an HTML comment (`<!--` and `-->`
   around the fence), so that the rendered page opens with prose.
+  **Imports**.  Every `open import` names what it takes, in a `using` clause
   or by `renaming` (a barrel re-exports with `public`).  Most modules group
   them under the comments `-- Imports from the Agda Standard Library`,
   `-- Imports from the Agda Universal Algebra Library` and `-- Imports from
   this library`.

### Definitions and proofs

+  **One lemma per idea**.  Prefer small named lemmas to long proofs: a lemma
   with a name says what a step of a proof is, and another proof can use it.
+  **A type signature on every definition**.  Every definition at the top
   level of a module, or of a named module inside it, carries its type
   signature.  Only local abbreviations go without, such as the definitions
   of a `where` clause or a private name for a projection
   (`private 𝑨 = proj₁ 𝑳`).
+  **Each definition is introduced**.  Give each definition a line comment
   directly above it, or name it in the prose before its block.  About two
   thirds of the library's top-level definitions meet this today, the rest
   sharing the prose of the block they are in; a new module is held to it for
   every definition.
+  **Citations**.  The reference throughout is R. Freese, J. Ježek and
   J. B. Nation, *Free Lattices* (American Mathematical Society, 1995), cited
   by the number of the theorem, lemma or corollary: "FJN Theorem 1.28" in a
   module's prose, or the reference link `[Freese, Ježek, and Nation
   (1995)][]` with the number ("Theorem 2.6").  Cite any other source the
   same way, by the number of the result; a well-known result goes by its
   name as well (Whitman's condition, Jónsson and Kiefer's theorem).

### Cost and barrels

+  A **barrel** is a module that only re-exports others, for its section of
   the library: `Lattices.Free` and `Lattices.Free.Canonical`.
+  A module that takes three seconds or more to check on its own (see [The
   cost of a module](#the-cost-of-a-module)) carries `check-cost: heavy` in
   its front matter, states its cost in its prose (the time, the date it was
   measured, and where the time goes, if known), and is imported by no
   barrel; the barrel's prose links it instead.  `git grep -l 'check-cost:
   heavy' src` lists the heavy modules.  `make check` still checks every one;
   the rule spares a reader who imports a barrel the cost.  No tool enforces
   it here, so the review checks it.

## What happens to a pull request

+  **Outside `src/`**.  A pull request that changes this guide, the README,
   the documentation site, the checks or CI is reviewed and merged here, as
   usual.
+  **Inside `src/`**.  A pull request that adds or changes a module is
   reviewed here like any other.  Once it is accepted, the maintainer carries
   the change into the library's source repository, and the next release
   publishes it here byte for byte; the pull request is then closed with a
   link to that release.  The module's front matter names you as its author,
   and the release's section of `CHANGELOG.md` credits you and the pull
   request.
+  **The review**.  The checks above must pass in CI: `check` (the
   type-check, `nix develop --command make check`), `ci` (shellcheck over the
   scripts, and the safety check's cases) and `site` (the documentation
   site, built and checked).  The reviewer then reads the module against the
   rules of this guide, checks each statement against the source it cites,
   and looks for a definition the library already has under another name: a
   concept the library or the Agda Universal Algebra Library already defines
   is used, not defined again.

### Commits and pull requests

+  Fork the repository, and make a branch for the issue, named after it
   (`12-short-description`).
+  Make each commit one coherent change, with a one-line summary and, for a
   change that is not trivial, a paragraph saying what it does and why.
+  Keep a pull request to one concern, and open it against `main`, naming
   the issue it addresses.
